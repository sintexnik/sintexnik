# Схема "Планировщик → Исполнитель → Судья"

Этот репозиторий настроен на трёхролевую схему экономии лимитов: дорогая модель (Opus)
включается только на планировании и финальной проверке, вся объёмная работа идёт на Sonnet.

## Роли

| Роль | Файл | Модель | Что делает | Что НЕ делает |
|---|---|---|---|---|
| **planner** | `.claude/agents/planner.md` | `claude-opus-4-8` | Разбирает задачу, формулирует критерии завершения, создаёт task-list | Не пишет и не редактирует файлы |
| **executor** | `.claude/agents/executor.md` | `claude-sonnet-5` | Пишет/правит код, делает код-ревью, тестирует сайты/приложения (Playwright) функционально и по производительности | Не решает стратегию, не выносит финальный вердикт |
| **judge** | `.claude/agents/judge.md` | `claude-opus-4-8` | Независимо перепроверяет код и результаты тестирования (свои прогоны, не отчёт executor), выносит вердикт | Не исправляет код/контент сам |

`executor` и `judge` подключены к Playwright через `mcpServers` в своей же frontmatter —
браузерные тулы доступны только им, в основную сессию не попадают и контекст не засоряют.

## Как вызывать

Естественным языком:
```
Используй planner-агента, чтобы спланировать [задача]
```

Явно (гарантированно запускает нужного агента, а не выбор Claude):
```
@agent-planner спланируй [задача]
```

Аналогично `@agent-executor`, `@agent-judge`.

## Обычный цикл (дёшево, по умолчанию)

1. `planner` разбирает задачу и создаёт task-list с критериями завершения.
2. Для каждой подзадачи вызывается `executor` — **можно вызывать его несколько раз
   подряд или параллельно** на разные подзадачи: каждый вызов получает своё чистое
   контекстное окно, поэтому объём задачи не ограничен окном одной модели.
3. Когда все подзадачи закрыты, вызывается `judge` — он проверяет результат по
   критериям планировщика с доказательствами (запуск тестов и т.п.), а не на слово.
4. Если `judge` возвращает «на доработку» — конкретный список замечаний уходит
   обратно в `executor`, цикл повторяется (по умолчанию не больше 5 итераций).

Одной командой весь цикл целиком можно запустить через `/plan-execute-judge [задача]`
(см. `.claude/commands/plan-execute-judge.md`).

### Готовая команда для цикла

Комбинируй с `/goal`, если нужен явный критерий остановки для одной конкретной подзадачи:
```
/goal Реализуй [подзадача].

Критерии завершения:
- [критерий 1]
- [критерий 2]

Остановись только когда все критерии выполнены. Максимум итераций: 5.
```

Для обработки списка однотипных подзадач — `/loop`:
```
/loop Обработай каждую подзадачу из task-list. После каждой — проверь на критерии.
Останови, когда список закончится.
```

## Эскалация: Agent Teams (дороже, но с прямым общением агентов)

По умолчанию `planner`, `executor` и `judge` — это обычные субагенты: они НЕ общаются
друг с другом напрямую, результат каждого возвращается в вызвавшую сессию, и именно
она решает, что делать дальше. Это и даёт основную экономию токенов.

В этом репозитории включён экспериментальный флаг `CLAUDE_CODE_EXPERIMENTAL_AGENT_TEAMS`
(см. `.claude/settings.json`), поэтому в любой момент можно попросить те же роли
работать как команда с прямым обменом сообщениями и общим task-list:

```
Spawn a team: planner as lead-adjacent coordinator, three executor teammates working
in parallel on independent modules, and a judge teammate reviewing each as it finishes.
```

Используй это **только** когда задачи реально независимы и выигрывают от параллельного
обсуждения (ревью с разных углов, конкурирующие гипотезы при отладке, независимые модули).
Документация Claude Code прямо предупреждает: команда агентов расходует токенов
значительно больше, чем цепочка субагентов — для последовательной работы или изменений
в одних и тех же файлах это не подходит.

## Использовать эти роли в других проектах

Чтобы эти три агента были доступны не только в этом репозитории, а во всех твоих
проектах на личной машине — скопируй файлы из `.claude/agents/` в `~/.claude/agents/`:

```bash
cp .claude/agents/*.md ~/.claude/agents/
```

(Файлы в `.claude/agents/` этого репозитория — версионируемая, командная копия;
`~/.claude/agents/` на твоей личной машине — твоя персональная копия поверх любого
проекта. Это два независимых места хранения, синхронизируются только вручную.)

## Обычный режим vs агентный режим — как явно переключаться

По умолчанию просто написанное в чат сообщение — это **обычный режим**: Claude отвечает
сам, максимум может по своей инициативе делегировать один субагент под капотом, если
описание задачи явно совпадёт с одним из `planner`/`executor`/`judge`. Полный цикл сам
по себе не запускается.

Два документированных, однозначных способа явно включить агентный режим:

1. **`/plan-execute-judge [задача]`** — наша команда (`.claude/commands/plan-execute-judge.md`).
   Гарантированно прогоняет весь цикл planner → executor → judge с доработкой до 5 итераций.
2. **`ultracode: [задача]`** или фраза **"используй workflow"** — встроенный в Claude Code
   официальный переключатель в более тяжёлый режим оркестрации (Dynamic Workflows): Claude
   сам пишет и исполняет скрипт, который управляет множеством агентов в фоне, не занимая
   твою основную ленту диалога. Это отдельная от наших субагентов система — использует
   `agent()`/`pipeline()` под капотом, доступна на платных планах (Pro и выше, `/config` →
   "Dynamic workflows"). Подходит для по-настоящему больших задач (аудит сотен файлов,
   массовая миграция) — не для повседневного цикла с тремя ролями, который и так дёшев.

Явных сигналов три: имя команды в начале сообщения, ключевое слово `ultracode`, или прямое
упоминание конкретного агента (`@agent-planner` и т.п.). Если ни одного из них нет — это
обычный режим, даже если тема разговора техническая.

## Быстрая перенастройка агентов

### Посмотреть, какая модель у агента сейчас
Модель зафиксирована в frontmatter файла, не привязана к `/model` основной сессии:
```
head -6 .claude/agents/planner.md   # видно поле model: claude-opus-4-8
```
В момент реального вызова агента модель также видна в транскрипте (`Ctrl+O` в CLI) и в
подписи задачи в панели агентов — там указано имя агента и его модель.

### Поменять модель или промпт агента
Правь файл напрямую — правки в `.claude/agents/*.md` подхватываются на лету, в течение
нескольких секунд, без перезапуска сессии (кроме случая, когда это самый первый файл в
только что созданной директории `agents/` — тогда нужен один перезапуск):
```yaml
---
name: executor
model: claude-sonnet-5   # поменяй на sonnet / opus / haiku / конкретный ID — подхватится сразу
---
Текст ниже YAML-шапки — это системный промпт агента, редактируется так же свободно.
```
Модель можно переопределить и разово, не трогая файл вообще — просто попроси при вызове:
*"Вызови executor на этот раз на haiku, не меняя файл"*.

### Что делать, если завтра нужен не код, а, например, проверка маркетинговой стратегии
Не переписывай `planner`/`executor`/`judge` поверх текущих — они специализированы под код
и тестирование (Playwright, pytest-подобные проверки), и это специализация имеет смысл
только для кода. Вместо этого заведи **параллельный набор с суффиксом домена**, по той же
трёхролевой схеме, но со своими инструментами:

```
Создай по аналогии с planner/executor/judge новую тройку агентов:
marketing-planner.md, marketing-executor.md, marketing-judge.md — для анализа
и проверки маркетинговой стратегии. Инструменты: WebSearch, WebFetch, Read, Write
вместо Bash/Playwright — им не нужно гонять тесты или открывать браузер, им нужно
искать рынок, конкурентов и данные. Модели те же: planner/judge — opus, executor — sonnet.
```

Оба набора агентов сосуществуют независимо (разные `name`), вызываются отдельно
(`@agent-marketing-planner` vs `@agent-planner`), ничего не ломают друг у друга.
